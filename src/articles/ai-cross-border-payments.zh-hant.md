## 1. 從支付工具，走向交易協作

我們認為，AI 對跨境支付的影響，可能不止是更快地填寫表格。當軟件能夠理解訂單、提出採購建議、調用服務時，交易的發起方式也可能改變。這是 AirDB 的方向判斷，不是對未來的確定預測，更不代表自主交易已經普遍成熟。

真正值得研究的問題是：人如何把目標交給軟件，同時保留對用途、額度和責任的控制？支付只是其中一環。授權之前的業務意圖、執行中的狀態，以及完成後的核對，都需要被連接起來。我們把跨境貿易作為具體起點，逐步理解這些基礎能力。

## 2. 一筆付款背後的工作

設想一家貿易平台處理供應商訂單。以下是虛構示例，不是客戶案例：業務人員確認採購，財務檢查付款條件，營運查詢外部付款結果，再把回執與訂單核對。每個環節都有自己的記錄，也可能出現名稱不一致、資訊缺失或狀態未更新。

如果只優化「發出付款請求」，前後的人工交接仍然存在。更有價值的目標，是讓每個事件能關聯到同一個業務意圖，讓負責人知道哪些資訊已確認、哪些仍需處理。這裏不假設所有企業都有同樣的問題，實際產品需要從訪談和具體流程中驗證。

## 3. 效率：先減少理解與核對的摩擦

AI 可以作為文件理解、資訊補齊建議和異常分類的輔助工具。我們希望驗證，它能否幫助團隊更快找到需要核查的欄位、歸集相關憑證、解釋對賬差異。模型給出的內容應可追溯到原始材料，並允許人修正。

這些都是待驗證的價值假設。不能從一段示範推導出到賬更快、手續費更低，或者業務可以完全無人處理。試驗應先定義基線：完成一次核對需要多少人工操作，誤判如何被發現，覆核耗時是否真的減少。外部通道的執行與最終結果仍需單獨確認。

## 4. 風控：把推理能力與金融權限分開

「能理解一項任務」不等於「有權付款」。我們擬議的控制包括主體身份、用途、收款對象、單筆與累計限額、有效期、撤銷和人工審批。Agent 提出意圖，策略決定能否繼續；超出授權或結果不明確時，進入拒絕或待處理流程。

授權不能由模型自行擴大。一次審批需要與具體請求關聯，策略改變和審批結果也應留下記錄。撤銷限制後續請求，不代表能夠逆轉已完成交易。未知結果更不能直接當作失敗再付款，否則重試可能製造新的問題。這些是設計原則，不是當前 AirDB 平台已經具備的認證或安全保證。

## 5. Agent 商業：從一次調用到一筆可解釋的支出

當 Agent 購買數據、調用模型或使用算力時，預算應該怎樣表達？我們建議從一個明確用途、一個允許的服務範圍開始，同時記錄請求、授權決定、交付結果和費用依據。任務結束後，負責人應能解釋為甚麼發生這筆支出。

小額高頻調用不一定適合逐筆支付。按次付費可以細化使用邊界，聚合計費則可能減少重複處理，但兩者都涉及失敗、重複請求和結算週期等權衡。具體選擇需要測量成本與業務風險，而不是假設「機器交易」天然即時、低成本或沒有爭議。

## 6. 協議、資產和通道，需要分別討論

x402 的 HTTP transport v2 使用 HTTP 402 表達付款要求，並通過 `PAYMENT-REQUIRED`、`PAYMENT-SIGNATURE` 與 `PAYMENT-RESPONSE` 傳遞要求、支付載荷與結果。這是協議文件描述的交互機制。[來源：x402 官方 HTTP transport 規範](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)。

協議機制不能證明某個產品已經接入，也不能替代對資產、網絡和執行通道的評估。數字人民幣支付技術是 AirDB 原有的探索方向，但本文不聲稱已有開放介面、通道資格或實際接入，更不把 x402 與數字人民幣畫上等號。未來任何整合都需要獨立驗證可用介面、職責與適用邊界。

## 7. 參考架構：讓每一步都有可核對的結果

我們的概念架構是：交易意圖 → 授權策略 → 支付編排 → 外部執行 → 回執與對賬。外部執行目前只是未來評估環節，沒有真實資金在本站流動。業務記錄用於理解流程，不是銀行餘額，也不等於最終清算證明。

工程上應研究請求冪等、明確狀態、重複回執處理、有限重試和異常隔離。重要的不是畫出更多服務框，而是明確每一步接受甚麼、輸出甚麼、誰處理不確定性。先在無資金原型中重現失敗和拒絕，再討論真實整合，比直接承諾交易吞吐量更有意義。

## 8. 漸進驗證，比提前承諾規模更重要

第一階段是理解客戶的問題，選擇一條訂單到對賬的流程，找到承擔責任的人。下一階段可以設計無資金原型，模擬身份、餘額和事件，驗證策略拒絕、人工覆核與重複請求。只有可重現的測試環境真正存在時，才稱它為沙盒。

有條件的合作試點，需要額外確認介面、合約、責任和運行支援。平台擴展則應由重複出現的客戶需求、留存價值、成本與可靠性證據推動。我們尚未回答所有渠道可得性和商業價值問題，也不會用未經驗證的時間表掩蓋這些未知。

例如，驗證可以記錄一次超額請求被拒絕、一次回執延遲進入待處理、一次重複請求沒有生成第二個執行動作。每個結果都需要可重現的輸入和可解釋的決定。只有這些基本行為經得起檢查，才有依據討論更廣的場景；模擬結果也不能自動代表真實通道表現。

## 9. AirDB 的下一步

AirDB 選擇面向 AI 與 Agent 時代的金融基礎設施方向，以跨境貿易切入，規劃支付編排、授權與風控、交易記錄與對賬，並探索 Agent 交易介面。我們希望與企業、平台和開發者，從一項可描述的問題開始共同設計。

本站提供研究與產品規劃，不提供錢包、託管、兌換、清算或實際支付服務，不暗示監管批准或官方關聯。如果你願意討論業務場景，可以介紹流程和待解決問題；請不要發送真實支付數據、帳戶憑證或身份材料。建設可信基礎設施，首先要清楚說明現在能做甚麼，以及還需要證明甚麼。
