## 1. 从支付工具，走向交易协作

我们认为，AI 对跨境支付的影响，可能不止是更快地填写表单。当软件能够理解订单、提出采购建议、调用服务时，交易的发起方式也可能改变。这是 AirDB 的方向判断，不是对未来的确定预测，更不代表自主交易已经普遍成熟。

真正值得研究的问题是：人如何把目标交给软件，同时保留对用途、额度和责任的控制？支付只是其中一环。授权之前的业务意图、执行中的状态，以及完成后的核对，都需要被连接起来。我们把跨境贸易作为具体起点，逐步理解这些基础能力。

## 2. 一笔付款背后的工作

设想一家贸易平台处理供应商订单。以下是虚构示例，不是客户案例：业务人员确认采购，财务检查付款条件，运营查询外部付款结果，再把回执与订单核对。每个环节都有自己的记录，也可能出现名称不一致、信息缺失或状态未更新。

如果只优化“发出付款请求”，前后的人工交接仍然存在。更有价值的目标，是让每个事件能关联到同一个业务意图，让负责人知道哪些信息已确认、哪些仍需处理。这里不假设所有企业都有同样的问题，实际产品需要从访谈和具体流程中验证。

## 3. 效率：先减少理解与核对的摩擦

AI 可以作为文档理解、信息补齐建议和异常分类的辅助工具。我们希望验证，它能否帮助团队更快找到需要核查的字段、归集相关凭证、解释对账差异。模型给出的内容应可追溯到原始材料，并允许人修正。

这些都是待验证的价值假设。不能从一段演示推导出到账更快、手续费更低，或者业务可以完全无人处理。试验应先定义基线：完成一次核对需要多少人工操作，误判如何被发现，复核耗时是否真的减少。外部通道的执行与最终结果仍需单独确认。

## 4. 风控：把推理能力与金融权限分开

“能理解一项任务”不等于“有权付款”。我们拟议的控制包括主体身份、用途、收款对象、单笔与累计限额、有效期、撤销和人工审批。Agent 提出意图，策略决定能否继续；超出授权或结果不明确时，进入拒绝或待处理流程。

授权不能由模型自行扩大。一次审批需要与具体请求关联，策略改变和审批结果也应留下记录。撤销限制后续请求，不代表能够逆转已完成交易。未知结果更不能直接当作失败再付款，否则重试可能制造新的问题。这些是设计原则，不是当前 AirDB 平台已经具备的认证或安全保证。

## 5. Agent 商业：从一次调用到一笔可解释的支出

当 Agent 购买数据、调用模型或使用算力时，预算应该怎样表达？我们建议从一个明确用途、一个允许的服务范围开始，同时记录请求、授权决定、交付结果和费用依据。任务结束后，负责人应能解释为什么发生这笔支出。

小额高频调用不一定适合逐笔支付。按次付费可以细化使用边界，聚合计费则可能减少重复处理，但两者都涉及失败、重复请求和结算周期等权衡。具体选择需要测量成本与业务风险，而不是假设“机器交易”天然即时、低成本或没有争议。

## 6. 协议、资产和通道，需要分别讨论

x402 的 HTTP transport v2 使用 HTTP 402 表达付款要求，并通过 `PAYMENT-REQUIRED`、`PAYMENT-SIGNATURE` 与 `PAYMENT-RESPONSE` 传递要求、支付载荷与结果。这是协议文档描述的交互机制。[来源：x402 官方 HTTP transport 规范](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)。

协议机制不能证明某个产品已经接入，也不能替代对资产、网络和执行通道的评估。数字人民币支付技术是 AirDB 原有的探索方向，但本文不声称已有开放接口、通道资格或实际接入，更不把 x402 与数字人民币画上等号。未来任何集成都需要独立验证可用接口、职责与适用边界。

## 7. 参考架构：让每一步都有可核对的结果

我们的概念架构是：交易意图 → 授权策略 → 支付编排 → 外部执行 → 回执与对账。外部执行目前只是未来评估环节，没有真实资金在本站流动。业务记录用于理解流程，不是银行余额，也不等于最终清算证明。

工程上应研究请求幂等、明确状态、重复回执处理、有限重试和异常隔离。重要的不是画出更多服务框，而是明确每一步接受什么、输出什么、谁处理不确定性。先在无资金原型中重现失败和拒绝，再讨论真实集成，比直接承诺交易吞吐量更有意义。

## 8. 渐进验证，比提前承诺规模更重要

第一阶段是理解客户的问题，选择一条订单到对账的流程，找到承担责任的人。下一阶段可以设计无资金原型，模拟身份、余额和事件，验证策略拒绝、人工复核与重复请求。只有可复现的测试环境真正存在时，才称它为沙盒。

有条件的合作试点，需要额外确认接口、合同、责任和运行支持。平台扩展则应由重复出现的客户需求、留存价值、成本与可靠性证据推动。我们尚未回答所有渠道可得性和商业价值问题，也不会用未经验证的时间表掩盖这些未知。

例如，验证可以记录一次超额请求被拒绝、一次回执延迟进入待处理、一次重复请求没有生成第二个执行动作。每个结果都需要可复现的输入和可解释的决定。只有这些基本行为经得起检查，才有依据讨论更广的场景；模拟结果也不能自动代表真实通道表现。

## 9. AirDB 的下一步

AirDB 选择面向 AI 与 Agent 时代的金融基础设施方向，以跨境贸易切入，规划支付编排、授权与风控、交易记录与对账，并探索 Agent 交易接口。我们希望与企业、平台和开发者，从一项可描述的问题开始共同设计。

本站提供研究与产品规划，不提供钱包、托管、兑换、清算或实际支付服务，不暗示监管批准或官方关联。如果你愿意讨论业务场景，可以介绍流程和待解决问题；请不要发送真实支付数据、账户凭证或身份材料。建设可信基础设施，首先要清楚说明现在能做什么，以及还需要证明什么。
