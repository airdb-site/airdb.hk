## 3. 客户、价值与商业模式假设

首要客户建议：有跨境供应商付款和多系统对账流程的 B2B 平台或贸易科技团队。买家假设是财务运营负责人，技术评估者是平台工程负责人。首次讨论聚焦一条“订单—审批—外部付款结果—对账”链路，而非所有国家、币种和人群。

价值假设：减少人工跨系统核对，让异常、授权责任和付款状态更清晰。AI 用于理解与辅助判断；确定性的策略决定是否进入下一步。没有测量前不承诺省钱比例、到账速度或风险下降。

第二客户：构建 Agent、付费 API、算力和数据服务的开发团队。验证预算约束、付费调用与回执如何协同。金融机构与通道服务方是潜在生态协作对象，不列为已有合作方。

建议商业模式依次验证：企业软件订阅（组织、工作流及管理能力）→按使用量计费（可计量的软件事件或 API 服务）→实施及企业支持。暂不公开套餐价格，不以汇差、资金沉淀收益或清算费建立商业叙事；费率与计量单位须在实际交付后验证。官网只有“讨论业务场景”，没有购买按钮或虚构免费试用。

建议开展 5–8 次目标团队访谈，数量为调研计划而非客户证据。询问当前流程、异常频率、人工核对时间、预算归属、可接受集成方式；成功信号是至少出现可复述的重复痛点、明确流程负责人及愿意共同定义无资金原型的团队。若只有一般兴趣，没有流程或预算负责人，先收窄场景，不扩大产品目录。

可持续规模来自共享领域模型、可靠工程、伙伴能力和客户留存，不来自首页写“全球领先”。未来职能建议按阶段建立产品与客户研究、平台工程、可靠性与安全、合作与专业合规支持；没有团队名单或招聘计划前不虚构组织架构与职位。技术公益可通过有证据的开源与知识分享体现。

## 4. 产品架构：一个平台，四类能力

以下名称为描述性工作名称，不是已上线产品或商标。首期官网以一张架构图和四个锚点解释，不创建四个空洞产品站。

| 能力 | 客户问题与拟议职责 | 不承担什么 | 当前对外状态 |
| --- | --- | --- | --- |
| 支付编排 | 关联订单与支付意图，组织审批、外部通道请求及状态 | 不意味着 AirDB 持有资金或拥有清算网络 | 规划 |
| 授权与风控 | 主体、用途、收款方、限额、时效、撤销及人工审批；辅助异常识别 | 不承诺消除欺诈，不让模型自行授予权限 | 规划 |
| 交易记录与对账 | 业务事件、外部回执、差异及核对状态；未来评估账本能力 | 业务记录不等于银行余额或最终清算证明 | 规划 |
| Agent 交易接口 | 将机器请求映射到受控意图；研究协议适配、付费 API 和小额调用 | 不是无限授权钱包；不是 x402 原生 e-CNY 的证明 | 探索 |

概念关系：业务系统 / 人 / Agent → 交易意图 → 授权策略 → 编排 → 外部通道（未来评估）→ 回执核对。所有步骤产生可关联的事件；异常返回人工处理。图中外部通道虚线框，标“未来接入评估”；不得使用像实时仪表盘的余额、流水或成功数字。

未来平台工程原则（非本轮后端方案）：组织与权限隔离、幂等请求、明确状态机、事件追踪、重试预算、重复回执处理、异常隔离、观测与恢复。协议适配与业务领域分离；在有实测负载前不承诺 TPS、多区域容灾或 SLA，也不提前决定微服务、区块链或数据库。真实金融系统需独立架构与责任评审。

### 状态词与证据规则

“愿景”是公司方向；“探索”是研究假设；“规划”是明确设计但未交付；“沙盒”必须有可验证、隔离真实资金的运行环境；“可用”必须有确定访问入口、范围、负责人和验证记录。初版金融能力仅使用探索/规划；本轮仅官网和阅读内容可访问。模拟代码明确“示意、不可作为生产接口”。状态变更须记录证据、日期、责任人并同步三语，不能仅改徽章。

## 5. 信任与权限边界

AI 可以建议或生成交易意图，不能绕过主体授权、扩大限额或批准自己的异常。规划中的策略检查覆盖身份、预算、用途、收款对象、有效期及撤销；失败和不确定结果默认进入拒绝/待处理，而非自动重付。撤销影响后续请求，不宣称能逆转已完成交易。风险规则与审计机制属于设计目标，不是当前平台认证。

网站明确：“本网站展示研究与产品规划，不处理真实支付，不提供钱包、托管、兑换或清算服务，不暗示监管批准或官方关联。”首页靠近主 CTA、能力页、开发者示例和页脚均有相应简明边界。信任页解释责任边界、拟议控制及当前网站数据实践，不展示认证徽章、服务状态 SLA 或监管许可占位图。

联系继续用现有邮件地址，仅引导描述场景和工作邮箱，不收账户、身份证件、支付凭证、私钥或真实交易数据。无需表单、CRM、分析追踪器和 cookie 弹窗。隐私文字说明站点无自建表单/账户，链接邮件由邮件服务处理；托管方可能处理访问日志，不能宣称“绝不收集数据”。主体/联系人未经确认前不编造隐私法定主体或地址；将事实核对作为发布前内容检查，暂不实现法律文书页。保留已有 Group 链接，但不扩写控股或子公司关系。

## 7. 核心专题与证据策略

标题必须保留用户原意：《AI重构跨境支付：效率、风控与Agent商业时代》。建议作为公司首篇完整观点文章，约 1800–2500 中文字，英文/繁中等义，不作为产品已交付公告。

文章结构：
1. 判断：AI 与 Agent 可能改变交易发起方式；这是 AirDB 的方向判断，不是必然预测。
2. 现有流程：订单、审核、付款状态与对账之间的人工连接；用明确虚构的贸易例子说明。
3. 效率：文档理解、信息补齐、异常分类、对账辅助；金融执行仍受渠道和授权约束。
4. 风控：模型输出与授权分离，收款方/用途/额度/时效、人审、撤销、审计；解释不确定状态不盲目重试。
5. Agent 商业：API、数据、算力采购的预算和回执；按次与聚合计费的权衡，不宣称所有小额支付都经济可行。
6. 技术分层：x402 协商层、资产/网络、通道与业务责任分别讨论；数字人民币探索独立成段。
7. 参考架构：意图→策略→编排→外部执行→核对；全部概念示意。
8. 渐进路线：无资金原型→验证问题→有条件试点；说明尚未解决的可靠性、商业价值和渠道可得性。
9. AirDB 的下一步与读者入口：产品探索与合作讨论，不提供现在接入付款的按钮。

证据台账每条记录 claim ID、命题、类别（外部事实/内部事实/观点/假设）、来源 URL 与版本、核对日期、支持范围、三语对应段落。外部技术事实优先协议原文；监管或金融服务事实只在需要时核对主管机构或官方资料，不凭文章概括作法律结论。数字人民币接入条件没有证据就只写探索，不补写开放 API 或资格。效率/成本指标没有实测就省略。

已核对的最小外部技术事实：x402 HTTP transport 用 HTTP 402 与 PAYMENT-REQUIRED、PAYMENT-SIGNATURE、PAYMENT-RESPONSE 组织需求、支付载荷与结果。来源：[x402 HTTP transport v2](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)，2026-10-31 读取；main 是可变引用，正式文章应固定当时 commit 或注明核对日期。此事实不证明 AirDB 接入、不证明 e-CNY 支持，也不证明全球可用。现有“目前主要用于稳定币”的时效判断在发布前需新证据，否则保留协议解释但改为更窄的“文档含特定资产与网络的示例”，不得把它当硬编码事实。

每篇研究显示作者（只使用实际确认身份；未确认则 AirDB 编辑）、发布日期、更新日期、观点/研究标识和来源。文章首页摘要不承诺产品性能。禁止虚构引用与案例，翻译不能把“计划”升级为“支持”。

## 9. 视觉与交互方向

建议延续现有米白、深绿、琥珀及自托管字体，形成理性、安静、有技术细节的公司感。保留品牌识别，不采用币价屏、虚构全球实时网络、银行式徽章或夸张 AI 发光球。Fraunces 用于英文标题，IBM Plex Sans 正文，Mono 仅用于协议和小标签；中文使用系统中文无衬线回退，确保不依赖新增字体 CDN。

桌面首页首屏约 55/45 文案与流程图，内容最大宽沿用约 1140px；移动端单列先文字、状态、CTA，再图。能力四项桌面 2×2，移动逐项；研究采用阅读型单栏与明确引用。配图用概念流程与文字，不展示未经授权的客户 Logo。主 CTA 每屏保持一个明确优先级。

菜单使用原生可访问交互，保留 Escape 与点击关闭。语言切换到当前对应页面，当前语言有非颜色指示。动画可不使用，若采用仅轻微出现效果并尊重 reduced-motion，不阻碍键盘或内容阅读。此方案提供结构方向，不在本轮制作可运行视觉原型。

## 10. 网站技术与多语言内容模型

沿用 Astro 静态站与当前依赖版本，不为公司规模更换框架。规模化官网首先靠可复用布局、内容治理与缓存友好的静态文件；金融后台另立项目，不能由官网框架推导。

建议拆分共享 Layout、Header、Footer、StatusBadge、CapabilityCard、FlowDiagram、ResearchLayout；从 content.ts 的平行数组逐步迁移为有稳定 ID 的对象，避免导航标签与链接顺序错配。品牌/路由/状态键共享，显示文案按语言保存。可采用普通 TypeScript 数据及本地 Markdown，无需 CMS、数据库或运行时服务；具体目录由实施者决定，切勿本轮升级 Astro。

内容实体建议：Page（id、locale、slug、title、description、sections）、Capability（id、status、summary、boundaries、evidenceRefs）、Research（translationKey、locale、title、summary、publishedAt、updatedAt、claimRefs、body）、Source（id、url、checkedAt、version、scope）。状态键统一，语言只翻译标签；引用和状态日期一致。核心页面缺任何语言或关键信息就阻止发布，不悄悄混用英文。中文编辑完成后人工核对繁中与英文专业术语。

每页独立 title/description、canonical、三语言 hreflang 与指向该页英文版的 x-default；sitemap 包含全部正式路由，404 noindex；语言路径与末尾斜线继续沿用。可见导航与抓取无需 JS。不得生成假 SDK 下载、假 API key、登录、账户页或未实现站内搜索。静态示例链接不发起交易请求。

维持原 GitHub Pages 构建部署机制，仅未来授权实施时处理；本轮不改工作流、CNAME、DNS。实施前重查 main 和工作区，任何新变更先保留与协调，不硬重置到本设计基线。

## 11. 非目标与验收

非目标：真实金融后台、支付执行、钱包/托管/兑换/清算、牌照与通道接入、KYC 服务、融资或客户数据室、付费订阅结账、CRM、招聘系统、CMS、框架升级、多区域交易系统。不得把官网上线视为这些事项交付。

设计交付验收：定位可用一句话复述；B 已记录；客户和商业假设有标签；四能力边界明确；保留迁移表、8 页范围、三语模型、专题证据与路线齐全；独立 builder check 无未处理的方向性缺口。用户批准的是这个方案，后续才编写实施计划。

未来官网验收（不是本轮已通过）：
- 24 个内容路由与 404、旧首页锚点、邮件/协议/Group 外链有效；语言切换保持同一页面。
- 三语信息等价，状态标签和安全边界一致；所有能力无运行证据则保持探索/规划。
- 核心专题三语完整，主张逐条关联来源或标观点；不出现虚构客户、资质、规模、收益和效能数字。
- 320/375/768/1440 宽度无横向溢出，长英文与中文导航可用；键盘、焦点、跳过链接、菜单关闭、404 返回正确，文字与交互符合 WCAG AA 对比度目标。
- 现有修复逐条回归，完整构建成功；检查静态输出 canonical/hreflang/sitemap，而非只看源文件。
- 无真实金融请求、凭证输入、伪表单提交；无新增跟踪或外部字体。性能以现站实测为基线防回退，不预先声称分数。
- 访客能说明“为谁、解决什么、目前处于什么阶段、下一步怎么联系”。建议用目标客户阅读反馈验证，不仅内部审美评价。
